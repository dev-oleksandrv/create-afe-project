# Documentation rules

Reference for creating, changing, and retiring documentation in this repository. `AGENTS.md`
holds the short rules and takes precedence if the two ever disagree; this file comes from the
project template, so report such a disagreement to the template (section 8) instead of editing it.
Other documents refer to the numbered sections below.

## 1. Principles

- Docs as code: documentation lives in this repository, in Markdown, changes through the same
  review as code, and is checked automatically (section 7).
- Progressive disclosure: entry files (`AGENTS.md`, `docs/README.md`) stay short and link out.
  Detail is read on demand. Nothing imports the whole tree.
- One owner per fact: `docs/README.md` maps kinds of facts to owner documents. Other documents
  link; they do not copy. Generated artefacts are produced by a script, checked in CI, and never
  hand-edited.
- Content before structure: a section exists only when it has real content. Future sections are
  listed in the map, not created as placeholders.
- Diátaxis is a lens for content type (reference, explanation, how-to, tutorial), not a mandatory
  folder tree at this stage.

## 2. Document kinds and formats

| Kind | Location | Format |
| --- | --- | --- |
| Agent rules | `AGENTS.md` | at most 90 template lines plus a project block of at most 10 lines (checked); numbered sections; `CLAUDE.md` imports it with `@AGENTS.md` |
| Documentation map | `docs/README.md` | tables of existing and planned sections |
| Contribution rules | `docs/contributing.md` | numbered sections: branches, commits, pull requests, and the pull request description template |
| Decision (ADR) | `docs/decisions/NNNN-title-with-dashes.md` | only for a decision that meets section 5; short MADR 4.0 from `adr-template.md`, about one page, details linked to their owner document; front matter `status`, `date`, `decision-makers`, `scope`, `summary`, optional `supersedes` |
| Decision index | `docs/decisions/README.md` | generated by `scripts/gen-decisions-index.sh` from the front matter of the records; never hand-edited |
| Plan | `docs/plans/<slug>.md` | front matter `status`, `owner`, `created`, `review-by`; sections Goal, Steps, Open questions |
| Requirement | `docs/requirements/` | one `REQ-NNN` per statement; RFC 2119 keywords; fields `status`, `source`, `verification` |
| Architecture | `docs/architecture/` | explanation and reference; front matter `status`, `date`, `verified-against` (commit, or `none` while no code exists) |
| Contract | `contracts/` | machine-readable, for example OpenAPI or JSON Schema; the file is the contract; prose links to it |
| Operations | `docs/operations/` | how-to; every procedure names the command or file it relies on |

This table is the fixed set of document kinds and locations that the template defines. Another
project document, such as a changelog, exists only when the owner approves it and the map lists
it; a new kind of document for every project is a change of the template. Front matter is YAML between `---` lines at the top of the file.

## 3. Status vocabulary

| Document | Allowed `status` values and transitions | Transition set by |
| --- | --- | --- |
| ADR | `proposed` to `accepted` or `rejected`; `accepted` to `deprecated` or `superseded by ADR-NNNN` | owner; agents create `proposed` |
| Requirement | `draft` to `approved` to `implemented` or `retired` | owner; `implemented` needs a linked test |
| Plan | `active`, then the file is deleted when done or abandoned | the change that completes or abandons it |
| Architecture, operations | `draft` to `current`; `current` with a stale `verified-against` is suspect | the reviewer who verified it against code |
| Owner decision in an owner document | a statement carries its document's status until the owner decides it; then it ends with, or its section opens with, `Decided by the owner, YYYY-MM-DD.` | owner; agents add the marker only on the owner's explicit instruction |

Wording rules for behaviour:

- "X does Y" is allowed only for implemented behaviour: merged code with a test. Link the test or
  module when the claim matters.
- Requirements use RFC 2119 keywords (MUST, SHOULD, MAY) and never claim to be implemented.
- Proposals say "proposed"; accepted decisions say "accepted" or "decided".
- Unknown things are written as "not decided" or "unknown", never guessed.

## 4. Currency

A document is current when its content agrees with its owner source (code, contract, decision).
`date` records the last content change. `verified-against: <commit>` records the last review
against code and is required for architecture and operations documents once code exists.
Touching a file or bumping a date is not verification.

## 5. Lifecycle

### Create

- A document is created when its first real content exists. A new section or plan needs the
  owner's approval; an agent may create an ADR with `status: proposed`, and the owner's
  acceptance is the approval.
- New ADR: only for a decision that is costly to reverse once code or data depend on it and that
  had a real alternative: language, runtime, or framework; storage and persistent data formats;
  public protocols and contract formats; the security, isolation, or authentication model; an
  external service or infrastructure dependency. Copy
  `adr-template.md`, take the highest existing number plus one, set `status: proposed`, record one decision in
  about one page, link the owner documents instead of listing rules or details, and regenerate
  the index: `scripts/gen-decisions-index.sh > docs/decisions/README.md`.
- Other owner decisions: an edit of the project's owner document (architecture, operations)
  carrying the marker of section 3; a decision about a template-owned file goes to the template
  (section 8). Requirements use their own status instead. Process
  rules live in the rule documents and their checks; an ADR records a process change only when
  it revises an existing ADR (section 8). Implementation choices stay in the pull request and the
  commit messages.
- New plan: only for work that spans more than one session or needs owner follow-up. Agent task
  plans stay in the conversation or the PR.
- New section: `docs/README.md` moves it from planned to existing in the same change.

### Update

- Update the owner document in the same change that makes it wrong: a behaviour change, a
  contract change, an operational change, an accepted decision.
- Internal refactoring that leaves behaviour, contracts, and operations unchanged needs no
  documentation change.
- Update links and the map. Never copy content from another document.

### Supersede

- An ADR that exists on `main` is not edited, whatever its status, except for its `status` line
  along a transition of section 3. A `proposed` ADR that needs other wording is `rejected` and
  replaced by a new ADR; an ADR is never deleted or renamed. A change edits freely only the ADRs
  it adds.
- `superseded by ADR-NNNN` names an ADR added by the same change. The new ADR lists the records
  it replaces in `supersedes`.
- Requirements are retired with a reason and a link to the replacing requirement or decision.

### Archive and delete

- Plans: the change that completes or abandons a plan deletes the file; git history is the
  archive. A plan past its `review-by` date must be updated and re-dated, or deleted, in the next
  change that touches `docs/`. Agents flag it in their report.
- There is no archive directory. A retired document that is still useful stays in place with its
  retired status.
- Temporary material (research notes, execution logs, transcripts, agent reports) never enters
  `docs/`. It lives in the conversation, the PR description, an issue, or scratch space until a
  person extracts durable facts into the owner document.

## 6. Alignment of documentation, contracts, and code

These rules apply once code exists; they are fixed now so the first code follows them.

- Contracts are machine-readable files in `contracts/`. The file is the source of truth for the
  interface. The implementation conforms to it, and prose documentation links to it. Contract
  linting and breaking-change detection are added to CI with the first contract, as decided in
  an ADR together with the contract format.
- Implemented behaviour is proven by tests. Documentation that describes behaviour links to the
  test or module. A described behaviour without a test is `proposed`, not `implemented`.
- Definition of done for a behaviour or interface change: code, tests, contract, and the owner
  document change in the same pull request. CI runs the documentation checks, the contract
  checks, and the tests on every pull request.
- Architecture documents carry `verified-against`; a review against code updates it.
- With the first code: the project adds its code checks to `scripts/checks.d/` (section 9), and
  `docs/README.md` moves "implemented behaviour" to existing.
- Every pull request gets the `docs-review` workflow: an AI review for missing documentation
  updates and rule violations, posted as comments and advisory (section 7).

## 7. Automated checks and semantic review

| Concern | Automated (`scripts/check.sh`, CI) | Semantic review, per change |
| --- | --- | --- |
| Markdown syntax and structure | markdownlint-cli2 | none |
| Broken internal links and anchors | lychee, offline, with fragments | none |
| External links | not checked automatically | author verifies when adding; spot check on review |
| Status correctness | none | status matches the evidence (section 3) |
| Invented facts | none | every new fact has a source or is marked unknown |
| Duplication | none | new content links instead of copying |
| Currency | none | `verified-against` and the map are updated |
| Documentation updated together with code | `docs-review` workflow on pull requests, advisory | reviewer confirms the owner document changed |
| ADRs on `main` change only their status line (section 5) | `scripts/check-decisions.sh`: Stop hook and `decisions` workflow | none |
| New ADRs carry `scope` and `summary`; the decision index matches the records | `scripts/check-decisions.sh`: Stop hook and `decisions` workflow | none |
| A new ADR meets the criteria of section 5 | none | `docs-review` reports it; the owner decides |
| Template-owned files unchanged; one project block in `AGENTS.md`; its line budget (sections 2 and 9) | `scripts/check-template.sh`: Stop hook and `docs` workflow | none |
| Project checks (section 9) | `scripts/check-project.sh` runs `scripts/checks.d/*.sh`: `scripts/check.sh` and `docs` workflow; a Stop hook only if the project adds one | as the project defines |
| Merge readiness (`contributing.md`, section 3) | `scripts/check-decisions.sh --ready`: `decisions` workflow; signals, does not block | owner decides whether to merge |
| Finishing with failing checks | Stop hook in Claude Code | none |
| Structure and rule changes | protect hook: owner prompt in Claude Code, denied headless | explicit, separate, owner-approved |

Semantic review checklist for any documentation change:

1. Each new statement has a status, and the status matches the evidence.
2. No requirement, default, or decision was invented; gaps are listed as open questions.
3. No content duplicates another document; links point to the owner.
4. The map (`docs/README.md`) and all links are updated; `scripts/check.sh` passes.
5. ADRs that exist on `main` (apart from their status line), template-owned files, the
   documentation map, and the structure are unchanged unless the change is explicitly about them.
6. A new ADR meets the criteria of section 5 and links details instead of listing them; every
   new `Decided by the owner` marker rests on the owner's instruction in the pull request.

## 8. Changing these rules

Template-owned files (section 9), including this file and `AGENTS.md` outside its project block,
change only in the project template and reach this repository through a template update
(`contributing.md`, section 5). A change to the documentation map or the structure is a dedicated
change approved by the owner, recorded as an ADR only when it revises an existing ADR.

Protected files are the template-owned files, the generated `.template/owned.sha256` and
`.copier-answers.yml`, the documentation map, `.claude/protected-paths` and the paths it lists, any
ADR that exists on `main`, and any ADR whose status is not `proposed`. In Claude Code the protect hook (`.claude/hooks/protect-docs.sh`) asks the owner to
confirm an edit of a protected file; in headless runs the edit is denied. For scripted,
owner-driven changes the owner starts Claude Code with `DOCS_GUARD=off` in its environment, which
also lifts the Stop hooks `.claude/hooks/stop-check-decisions.sh` and
`.claude/hooks/stop-check-template.sh`. Other agents are bound by
`AGENTS.md` and the pull request review only.

## 9. Ownership of files

Every file belongs to exactly one class:

| Class | Files | Changed by |
| --- | --- | --- |
| Template-owned | the files listed with their hashes in `.template/owned.sha256` (rules, ADR template, checks, hooks, skills, workflows, linter configuration), and `AGENTS.md` outside its project block | a release of the template, applied with `copier update --trust` (`contributing.md`, section 5); never edited in this repository |
| Seeded | `README.md`, `CLAUDE.md`, `.gitignore`, `docs/README.md`, `.claude/protected-paths`, and the project block of `AGENTS.md`: created once by the template | the project |
| Generated | `docs/decisions/README.md`, `.template/owned.sha256`, `.copier-answers.yml` | their generator only |
| Project | everything else, including the documentation sections of section 2 and the extension points below | the project |

The project extends the template only at its extension points: checks in `scripts/checks.d/*.sh`,
run in name order by `scripts/check.sh` and by the `docs` workflow, which provision any tool they
need beyond Git, Node.js, lychee, and jq; Stop hooks in `.claude/hooks/project/stop/*.sh`, which
receive the Stop hook input and block the agent by exiting with 2; its own workflows in
`.github/workflows/` next to the template's, for example a code CI with its setup steps; extra
protected paths in `.claude/protected-paths`. Checks and Stop hooks are committed with their
executable bit. Personal
Claude Code settings go into `.claude/settings.local.json`, which is not committed.
`scripts/check-template.sh` fails when a template-owned file differs from its recorded hash or
when `AGENTS.md` does not contain exactly one project block.
